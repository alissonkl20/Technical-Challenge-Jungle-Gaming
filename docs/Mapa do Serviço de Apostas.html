01 · CONFIGURAÇÃO

Processos e infraestrutura

Um único código e uma única imagem Docker, executados como processos separados. Eles não conversam entre si pela rede: coordenam tudo pelo PostgreSQL. O SQS só transporta mensagens.

API HTTP :3000

Contrato do provedor: wallets, transações, consultas, reconciliação, /health e /metrics.

sqs-event-consumer :9465

Lê comandos da fila FIFO, deduplica pelo Inbox e só faz ACK depois do commit. Erro permanente vai para a DLQ.

outbox-publisher :9464

Reserva eventos da Outbox com lease, publica no SQS, faz retry com backoff e marca FAILED após 6 tentativas.

pending-reference-worker :9466

Retoma transações em PENDING_REFERENCE (5 s, 10 s, 20 s… até 1 h; expira em 24 h) e a compensação pós-COMMIT.

PostgreSQL :5432

Decide tudo: lock por wallet, idempotência por ON CONFLICT, CHECK, UNIQUE, FK composta e triggers.

migrate

Aplica as migrations versionadas (bun run migration:up) antes da API e dos workers subirem.

02 · DADOS

Tabelas e relacionamentos

03 · EXECUÇÃO

Ciclo de ponta a ponta de uma BET

Do pedido do provedor até o evento chegar na fila. HTTP e SQS entram em pontos diferentes, mas a partir do passo 3 seguem exatamente o mesmo caminho.

sequenceDiagram
  autonumber
  participant P as Provedor
  participant A as API / sqs-consumer
  participant U as Caso de uso
  participant D as PostgreSQL
  participant O as outbox-publisher
  participant Q as SQS (eventos)

  P->>A: POST /wagering/transactions (Idempotency-Key)
  A->>A: autentica + valida payload (400 se inválido)
  A->>U: comando BET 25.00 BRL
  U->>D: BEGIN
  U->>D: INSERT financial_operations ON CONFLICT
  alt chave já existe
    D-->>U: operação gravada
    U-->>A: replay (mesma resposta) ou 409
  else chave nova
    U->>D: SELECT wallet FOR UPDATE (lock)
    U->>U: regras: saldo, referência, rodada
    U->>D: INSERT wager_transactions (PROCESSED)
    U->>D: INSERT wallet_ledger_entries (DEBIT)
    U->>D: UPDATE wallets (100.00 → 75.00, version+1)
    U->>D: INSERT outbox (2 eventos)
    U->>D: UPDATE financial_operations (snapshot)
    U->>D: COMMIT
    U-->>A: PROCESSED, saldo 75.00
  end
  A-->>P: 200 + JSON (no SQS: ACK da mensagem)
  O->>D: reserva eventos (SKIP LOCKED + lease)
  O->>Q: publica WagerTransactionProcessed e WalletBalanceChanged
  O->>D: marca published_at
  Q-->>P: provedor consome os eventos
  1. Antes da transação
  2. AutenticaçãoHeaders X-Provider-Code e X-Provider-Key, comparação em tempo constante. Falha responde 401; provider de outro escopo, 403.
  3. Validação do payloadCampos desconhecidos, "1e3", mais de duas casas ou kind: "OPENING" respondem 400 e não gravam nada.
  4. Dentro de uma única transação PostgreSQL
  5. Reserva da idempotênciaSó o banco arbitra corrida entre instâncias. Se a chave existe com o mesmo hash, devolve a resposta gravada; com hash diferente, 409.INSERT INTO financial_operations … ON CONFLICT DO NOTHING
  6. Lock da walletSerializa só esta wallet. Wallets diferentes seguem em paralelo.SELECT … FROM wallets WHERE id = $1 FOR UPDATE
  7. Regras de negócioSaldo suficiente, referência existe e pertence ao mesmo jogador, wallet, moeda e rodada, BET ainda sem resultado. Se falhar: REJECTED + failureCode, sem mexer no saldo.
  8. Grava o fato, o lançamento e o saldoTransação de aposta, lançamento no Ledger e saldo novo. Triggers conferem a aritmética.INSERT wager_transactions · INSERT wallet_ledger_entries · UPDATE wallets
  9. Grava os eventos na OutboxO envelope final do evento é gravado junto, para nunca sair um evento de algo que não foi confirmado.INSERT INTO outbox (id = eventId, payload)
  10. COMMITTudo ou nada. Se o processo morrer antes, o PostgreSQL desfaz e o reenvio processa do zero.
  11. Depois do commit
  12. Resposta ou ACKHTTP devolve o JSON com o status certo (200, 202, 422). No SQS, o ACK acontece só agora.
  13. Publicação assíncronaO outbox-publisher reserva lotes com SKIP LOCKED, publica no SQS e marca como publicado. Se cair no meio, o lease expira e outro publica com o mesmo eventId.

      06 · INTEGRAÇÃO
      
Como um provedor integra a API

      
O caminho completo, do cadastro até a primeira aposta liquidada. Todas as rotas do provedor usam os mesmos dois headers de autenticação.

    

    
Antes de começar: a chave do provedor não é devolvida por nenhuma rota. Ela é configurada pelo operador em PROVIDER_API_KEYS e entregue ao provedor por um canal seguro. Use HTTPS fora do ambiente local.

Trate cada código de resposta

        
A regra de ouro: em erro de infraestrutura ou timeout, reenvie com a mesma Idempotency-Key e o mesmo payload. Nunca gere uma chave nova para tentar de novo.
